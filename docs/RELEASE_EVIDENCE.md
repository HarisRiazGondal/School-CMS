# Release evidence and status accounting

The project keeps eight equally weighted pilot milestones. Seven currently meet their local acceptance criteria. Production pilot release remains in progress until PostgreSQL, privacy/security, uploads, SMTP, backup restoration, accessibility and hosted pilot acceptance are evidenced. Implementation progress is 7/8 (87.5%); this is not a production-readiness percentage.

`docs/ai-context/project_state.json` records nine operational gates separately from that score. `python scripts/render_status.py` validates the state before rendering the offline dashboard. It rejects inconsistent passed/skipped/failed totals, a changed milestone denominator, weakened production criteria, incomplete gate records, or a readiness label that disagrees with the production milestone. Closing the production milestone requires every gate to be recorded as verified, each with a full commit SHA, timezone-aware timestamp, target, evidence artifact reference and reviewer.

This is schema and accounting validation. It does not authenticate an artifact, prove its contents or establish reviewer identity. A trusted operator must independently review each report against the executed source and deployment target before changing a gate to verified. Synthetic fixtures in unit tests exercise the validator only; they are not release evidence. Local code/configuration tests, hosted CI, target runtime measurements and human acceptance are different evidence sources and must stay distinguishable.

Use `manage.py verify_release --json` for runtime preflight, the guarded recovery rehearsal for PostgreSQL plus private files, and the isolated browser harness for synthetic role journeys. Their runbooks explain scope and limitations. Keep sensitive reports and real school data out of this repository. Record restricted artifact references without credentials or student identifiers. A CI success cannot substitute for target-host or human acceptance.
